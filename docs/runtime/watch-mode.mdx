Bun supports two kinds of automatic reloading:

- `--watch` mode, which hard restarts Bun's process when imported files change.
- `--hot` mode, which soft reloads the code (without restarting the process) when imported files change.

---

## `--watch` mode

Watch mode works with `bun test` and `bun build`, and when running TypeScript, JSX, and JavaScript files.

To run a file in `--watch` mode:

```bash terminal icon="terminal"
bun --watch index.tsx
```

To run your tests in `--watch` mode:

```bash terminal icon="terminal"
bun --watch test
```

To type check before every restart, add [`--check`](/runtime/check#watch-mode). After a type error, Bun waits for your next change instead of running the file.

```bash terminal icon="terminal"
bun --watch --check index.tsx
```

In `--watch` mode, Bun keeps track of all imported files and watches them for changes. When a file changes, Bun restarts the process with the same CLI arguments and environment variables as the initial run. If Bun crashes, `--watch` attempts to restart the process.

Bun also watches the [`.env` files](/runtime/environment-variables) it loaded at startup, such as `.env`, `.env.local` and any file passed with `--env-file`. Editing one of them restarts the process too, so the new values take effect without a manual restart.

<Note>

**⚡️ Reloads are fast.** The filesystem watchers you're probably used to have several layers of libraries wrapping the native APIs or, worse, rely on polling.

Instead, Bun uses the operating system's native filesystem watcher APIs, like kqueue or inotify, to detect file changes. Bun also applies several optimizations to scale to larger projects, such as setting a high rlimit for file descriptors, statically allocating file path buffers, and reusing file descriptors when possible.

</Note>

The following examples show Bun live-reloading a file as you edit it, with VSCode configured to save the file [on each keystroke](https://code.visualstudio.com/docs/editor/codebasics#_save-auto-save).

```sh terminal icon="terminal"
bun run --watch watchy.tsx
```

```tsx title="watchy.tsx" icon="/icons/typescript.svg"
import { serve } from "bun";

console.log("I restarted at:", Date.now());

serve({
  port: 4003,
  fetch(request) {
    return new Response("Sup");
  },
});
```

<Note>
  The **`--no-clear-screen`** flag, like TypeScript's `--preserveWatchOutput`, keeps Bun from clearing the terminal in
  watch mode. Use it when running multiple `bun build --watch` commands at the same time with a tool like
  `concurrently`, where one instance clearing the screen could hide another's errors: `bun build --watch
  --no-clear-screen`.
</Note>

<Note>
  Before each restart, `bun run --watch` runs the handlers your script registered for the kill signal. The default is
  `SIGTERM`, matching the signal Node.js sends its watched process. Use **`--watch-kill-signal`** to pick a different
  signal, e.g. `bun --watch --watch-kill-signal SIGINT index.ts`.
</Note>

## `--hot` mode

Use `bun --hot` to enable hot reloading when executing code with Bun. Unlike `--watch` mode, Bun doesn't hard-restart the entire process. It detects code changes and updates its internal module cache with the new code.

<Note>
  Bun's `--hot` is not the same as hot reloading in the browser. Many frameworks provide a "hot reloading" experience,
  where you can edit & save your frontend code (say, a React component) and see the changes reflected in the browser
  without refreshing the page. Bun's `--hot` is the server-side equivalent of this experience. To get hot reloading in
  the browser, use a framework like [Vite](https://vite.dev).
</Note>

```bash terminal icon="terminal"
bun --hot server.ts
```

Starting from the entrypoint (`server.ts` in this example), Bun builds a registry of all imported source files (excluding those in `node_modules`) and watches them for changes. When a file changes, Bun performs a "soft reload". Bun re-evaluates all files, but global state (notably, the `globalThis` object) persists.

Environment variables are read once at startup, so a soft reload cannot apply a changed `.env` file. When one of the `.env` files Bun loaded changes, `--hot` restarts the process instead, like `--watch` does. (On Windows, `--hot` does not watch `.env` files.)

```ts title="server.ts" icon="/icons/typescript.svg"
// make TypeScript happy
declare global {
  var count: number;
}

globalThis.count ??= 0;
console.log(`Reloaded ${globalThis.count} times`);
globalThis.count++;

// prevent `bun run` from exiting
const interval = setInterval(function () {}, 1000000);

// stop this version's interval before the next version starts its own
import.meta.hot.dispose(() => clearInterval(interval));
```

If you run this file with `bun --hot server.ts`, you'll see the reload count increment every time you save the file. Bun does not restart the process, so what a module starts at the top level keeps running after a reload: timers, event listeners, child processes, workers, file watchers. [`import.meta.hot.dispose()`](#import-meta-hot) is where a module stops them.

```bash terminal icon="terminal"
bun --hot server.ts
```

```txt
Reloaded 0 times
Reloaded 1 times
Reloaded 2 times
```

Traditional file watchers like `nodemon` restart the entire process, so HTTP servers and other stateful objects are lost. By contrast, `bun --hot` reflects the updated code without restarting the process.

### HTTP servers

You can update your HTTP request handler without shutting down the server: when you save the file, Bun reloads the server with the updated code without restarting the process. This results in seriously fast refresh speeds.

```ts title="server.ts" icon="/icons/typescript.svg"
globalThis.count ??= 0;
globalThis.count++;

Bun.serve({
  fetch(req: Request) {
    return new Response(`Reloaded ${globalThis.count} times`);
  },
  port: 3000,
});
```

### `import.meta.hot`

Under `bun --hot`, each of your modules has an `import.meta.hot` object. It has the part of the [Vite HMR API](https://vite.dev/guide/api-hmr) that applies when Bun evaluates every file again on each change.

```ts title="server.ts" icon="/icons/typescript.svg"
// `data` survives reloads of this module.
const state = (import.meta.hot.data.state ??= { reloads: 0 });
console.log(`reloaded ${state.reloads++} times`);

// This version of the module owns the child process.
const child = Bun.spawn(["bun", "worker.ts"], { stdout: "inherit" });

import.meta.hot.dispose(async () => {
  // Runs on the next reload, before Bun evaluates any module again.
  child.kill();
  await child.exited;
});
```

| Property      | Description                                                                                                                                                                 |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data`        | An object that Bun keeps across reloads, one per module. It starts out as `{}`. Bun keeps what you change in it, and what you assign to it.                                 |
| `dispose(cb)` | Registers a callback. On the next reload, Bun calls every registered callback with its module's `data`, in the order of registration, before it evaluates any module again. |
| `accept()`    | Does nothing. `bun --hot` evaluates every module again on each change, so every module already accepts its own updates.                                                     |

`decline()`, `on()` and `off()` also exist and do nothing. So do `prune()`, `invalidate()` and `send()` of Vite's API, which Bun's types do not declare. A module written for Vite or for Bun's dev server can call them under `--hot`.

How `dispose()` runs:

- Callbacks run in the order in which your modules registered them. A module that you load with a static `import` registers before the module that imports it.
- Bun runs the callbacks of a module that the new code no longer imports, so `prune()` has nothing to do.
- If callbacks return promises, Bun waits until all of them settle. There is no timeout, so return a promise only for work that ends. Bun stops waiting when the event loop has no work left that could settle them.
- A reload that waits includes the changes that you save during the wait.
- While Bun waits, timers and I/O run as usual, also after an uncaught error.
- Bun prints an error that a callback throws, and the reason of a promise that rejects. The other callbacks still run and the reload goes on.

Bun already carries some things across a reload, and they need no callback:

- [`Bun.serve()`](#http-servers) hands its new handlers to the server that is listening.
- [`Bun.SQL`](/runtime/sql#hot-reloading) takes over the open connections of the previous load.
- Bun stops the jobs of [`Bun.cron`](/runtime/cron) and registers the new ones.

To get a new server on every reload, stop the old server in `dispose()`. `server.stop()` frees the port at once, and the next version's `Bun.serve()` binds it again. The promise that `server.stop()` returns settles when the last connection closes, so the callback does not return it.

```ts title="server.ts" icon="/icons/typescript.svg"
const server = Bun.serve({
  port: 3000,
  fetch: () => new Response("a new server on every reload"),
});

import.meta.hot.dispose(() => {
  server.stop();
});
```

#### Where `import.meta.hot` exists

| The module                                                         | `import.meta.hot` | `import.meta.hot.dispose(...)` | `import.meta.hot.data`  |
| ------------------------------------------------------------------ | ----------------- | ------------------------------ | ----------------------- |
| Your modules under `bun --hot file.ts`, ES modules and CommonJS    | the object        | registers the callback         | the module's object     |
| A package in `node_modules`                                        | `undefined`       | Bun removes the call           | a new `{}` on each read |
| The code of `bun --hot -e`, or a script from standard input        | `undefined`       | Bun removes the call           | a new `{}` on each read |
| A `Worker`, a macro, a compiled executable                         | `undefined`       | Bun removes the call           | a new `{}` on each read |
| Without `--hot`: `bun file.ts`, `--watch`, `bun test`, `bun build` | `undefined`       | Bun removes the call           | a new `{}` on each read |

A package keeps `undefined` because a published package uses `if (import.meta.hot)` to ask whether a dev server drives it. A package that you link, or a workspace package, is one of your modules, unless you run with `--preserve-symlinks`.

The same file can run with and without `--hot` when it uses these forms:

```ts title="server.ts" icon="/icons/typescript.svg"
// OK in every mode: a call written in full. Without --hot, Bun removes it.
import.meta.hot.dispose(() => {});

// OK in every mode: one expression that reads and initializes `data`.
const state = (import.meta.hot.data.state ??= { reloads: 0 });

// Only with --hot: `hot` is undefined elsewhere, so guard what uses it.
if (import.meta.hot) {
  const hot = import.meta.hot;
  hot.dispose(() => {});
}
```

Call a method where you name it. Without `--hot`, a method that you name without a call, such as `register(import.meta.hot.dispose)`, is `undefined`.

In a `ShadowRealm`, `import.meta.hot` is `undefined` and Bun keeps the call, so guard it there.

Inside `if (import.meta.hot)`, a module written for the browser can use `document` or `window`. The guard is true under `--hot`, so check for those too.

A `--preload` script is evaluated once per process, not once per reload. A `dispose()` callback that it registers runs on the first reload only. If the entrypoint also imports the script, Bun reloads it like any other module.

With `--watch`, Bun restarts the process and calls no `dispose()` callback. To run code before a restart, listen for the kill signal that the `--watch` section above describes.

<Note>
  The dev server of Bun's bundler implements more of this API, such as per-module accept boundaries. See [Hot
  reloading](/bundler/hot-reloading).
</Note>

<Accordion title="Implementation details">

On hot reload, Bun:

- Runs the `import.meta.hot.dispose()` callbacks registered since the previous reload, and waits for any promises they returned
- Resets the internal `require` cache and ES module registry (`Loader.registry`)
- Runs the garbage collector synchronously (to minimize memory leaks, at the cost of runtime performance)
- Re-transpiles all of your code from scratch (including sourcemaps)
- Re-evaluates the code with JavaScriptCore

This implementation isn't particularly optimized. It re-transpiles files that haven't changed. It makes no attempt at incremental compilation. It's a starting point.

</Accordion>

## Files that are not imported

Both modes watch the files your code imports. Templates, SQL files, a config file read with `fs`, the output of another build: nothing imports those, so a change to them goes unnoticed. Two flags change what is watched. They work with `bun run` under `--watch` and `--hot`, and with `bun test --watch`.

### `--watch-path`

`--watch-path` takes a file or a directory to watch in addition to the imported files. A directory is watched recursively. Repeat the flag for more than one path.

```bash terminal icon="terminal"
bun --watch --watch-path ./views --watch-path ./config.json server.ts
```

A change below `./views` or to `config.json` now restarts the process, exactly like a change to an imported file. With `--hot` it reloads in place instead:

```bash terminal icon="terminal"
bun --hot --watch-path ./views server.ts
```

As in Node.js, `--watch-path` on its own turns on `--watch`. Unlike Node.js, imported files stay watched.

```bash terminal icon="terminal"
bun --watch-path ./views server.ts      # same as: bun --watch --watch-path ./views server.ts
bun test --watch-path ./fixtures        # rerun the tests when a fixture changes
```

- Relative paths are resolved against the working directory. A symlink is followed.
- The path does not have to exist yet, and neither do the directories above it. Bun notices when it is created, and when a watched directory is deleted and created again (`rm -rf dist && bun run build`).
- Changes inside `node_modules` and `.git` directories below a watched directory are ignored. Without that, every `bun install` and every `git` command would restart your process.
- Prefer the directories you care about over the project root: on Linux, watching a directory recursively costs one inotify watch per subdirectory, `node_modules` included.
- Write `./test` or `--watch-path=test` for a directory that is named like a Bun command (`test`, `build`, `run`, ...). A bare `bun --watch-path test server.ts` is read as `bun test`.

<Note>
  Changes to a `--watch-path` path are noticed on the main thread, between two turns of the event loop. A script that
  blocks the event loop for a long time (an infinite loop, a long synchronous computation) is restarted by a change to
  one of its imported files, but not by a change to a `--watch-path` path until the event loop runs again. With `bun
  test --isolate` (without `--parallel`), the paths are watched again in the fresh global of each test file, so a change
  that lands while one test file hands over to the next can be missed. Save the file again to rerun.
</Note>

### `--watch-exclude`

`--watch-exclude` takes a [glob](/runtime/glob). A file that matches is never watched: changing it does not restart or reload the process, whether your code imports it or it sits below a `--watch-path` directory. Repeat the flag for more than one pattern.

```bash terminal icon="terminal"
# another tool rewrites src/generated/ while the server runs
bun --watch --watch-exclude src/generated server.ts

# reload for the server code, never for the client components it also imports
bun --hot --watch-exclude '**/*.tsx' server.ts

# only restart for what is in src/
bun --watch --watch-exclude '!src/**' server.ts
```

- A relative pattern is relative to the working directory (`../shared` works). A pattern can also be absolute.
- A pattern covers what it matches and everything below it, so `src/generated` excludes the directory and all of its contents.
- A leading `!` negates the pattern: everything that does not match is excluded.
- As everywhere in Bun, `*` does not cross a `/`: use `**/*.tsx` for "every `.tsx` file", not `*.tsx`.
- On Windows a `\` in a pattern is a path separator, so write `/` or `\` as you like, and nothing can be escaped.
