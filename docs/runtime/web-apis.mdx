Some Web APIs, like the [DOM API](https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API#html_dom_api_interfaces) and [History API](https://developer.mozilla.org/en-US/docs/Web/API/History_API), aren't relevant in a server-first runtime like Bun. Many others are broadly useful outside the browser; when possible, Bun implements these Web-standard APIs instead of introducing new ones.

Bun partially or completely supports the following Web APIs.

## Web Storage

`sessionStorage` is a [`Storage`](https://developer.mozilla.org/en-US/docs/Web/API/Storage) that lives as long as the process. Every `Worker` has its own.

```ts
sessionStorage.setItem("theme", "dark");
sessionStorage.theme; // "dark"
sessionStorage.length; // 1
```

`localStorage` is kept in a file, and is a global only when `--localstorage-file` says which file. Without the flag `localStorage` is not defined.

```ts counter.ts
const runs = Number(localStorage.getItem("runs") ?? 0) + 1;
localStorage.setItem("runs", String(runs));
console.log(`run ${runs}`);
```

```sh
$ bun --localstorage-file=./local-storage.db counter.ts
run 1
$ bun --localstorage-file=./local-storage.db counter.ts
run 2
```

- The file is an SQLite database in the format that Node.js uses for its `--localstorage-file`, so the two runtimes can share one. It is created the first time `localStorage` is used. A relative path is resolved against the directory that the process started in.
- Several processes, and the `Worker`s of a process, can have the same file open. Each of them sees what the others write. The flag is for the whole process: a `Worker` cannot be given another file.
- `--localstorage-file=:memory:` is a `localStorage` that is not written anywhere, which is what a test run usually wants: `bun test --localstorage-file=:memory:`.
- A storage holds up to 10 MB of keys and values, counted as two bytes per UTF-16 code unit. A write that would go past that throws a `DOMException` named `QuotaExceededError`.
- Neither belongs to a request or a user. Everything that runs on a thread has the same `sessionStorage`, and everything that opens the file has the same `localStorage`, so a server should not put the data of one request or one user into them. With `:memory:` every `Worker` has a `localStorage` of its own.

## FileReader

[`FileReader`](https://developer.mozilla.org/en-US/docs/Web/API/FileReader) reads a `Blob` or a `File` and reports the outcome with events. It is there for code and libraries that were written for the browser, for example a library that takes the `File` of an upload. New code can call [`blob.text()`, `blob.arrayBuffer()` and `blob.bytes()`](/runtime/file-io#reading-files-bun-file) instead.

```ts
const server = Bun.serve({
  async fetch(request) {
    const form = await request.formData();
    const file = form.get("avatar") as File;

    const reader = new FileReader();
    const loaded = Promise.withResolvers<string>();
    reader.onload = () => loaded.resolve(reader.result as string);
    reader.onerror = () => loaded.reject(reader.error);
    reader.readAsDataURL(file);

    return new Response(await loaded.promise); // data:image/png;base64,iVBORw0KGgo...
  },
});
```

- `readAsArrayBuffer()`, `readAsText()`, `readAsDataURL()` and `readAsBinaryString()` take any `Blob`, including a [`Bun.file()`](/runtime/file-io). `readAsText()` decodes with the encoding it is given, then with the `charset` of the blob's type, then as UTF-8. A byte order mark wins over all three. `readAsDataURL()` uses `blob.type` as it is, and Bun gives some text types a charset: a `text/plain` blob reads as `data:text/plain;charset=utf-8;base64,...`.
- A read fires `loadstart` when the first chunk has arrived, then `progress`, then `load` and `loadend`. `progress` is fired for the first chunk, then at most every 50 milliseconds, and once more when all of the blob has been read. The read goes on when the listeners of an event have run, so `abort()` in a `progress` listener stops it there. Every event is a [`ProgressEvent`](https://developer.mozilla.org/en-US/docs/Web/API/ProgressEvent), which is a global too, with the bytes read so far in `loaded` and the size of the blob in `total`.
- A read that fails fires `error` and `loadend`, and no `loadstart` when it fails before its first chunk. `reader.error` is then a `DOMException` named `NotFoundError` for a file or an S3 object that does not exist and `NotReadableError` otherwise. Its `cause` is the error of the file system or of S3.
- `abort()` fires `abort` and `loadend` before it returns, and sets `reader.error` to an `AbortError`.
- A second read on a reader that is still reading throws an `InvalidStateError`. Use one reader for each blob, or wait for `loadend`.

## Unhandled rejections

When a promise is rejected and nothing handles the rejection, Bun dispatches [`unhandledrejection`](https://developer.mozilla.org/en-US/docs/Web/API/Window/unhandledrejection_event) on the global object, as a browser does on `window` and on the global object of a worker. The event is a [`PromiseRejectionEvent`](https://developer.mozilla.org/en-US/docs/Web/API/PromiseRejectionEvent) with the `promise` and the `reason`. A listener that calls `event.preventDefault()` has handled the rejection.

```ts
addEventListener("unhandledrejection", event => {
  console.error("unhandled rejection:", event.reason);
  event.preventDefault(); // Bun prints nothing itself, and the exit code stays 0
});

Promise.reject(new Error("boom"));
```

- The listeners are called before those of [`process.on("unhandledRejection")`](https://nodejs.org/api/process.html#event-unhandledrejection). If none of them cancels the event, everything goes on as it does without them: `process` is told, or Bun prints the error and the process ends with exit code 1.
- `event.preventDefault()`, or `return false` from an `onunhandledrejection` handler, makes the rejection handled with every value of `--unhandled-rejections`. Nothing is printed, the exit code is not set, `process` is not told, and `strict` and `throw` raise no `uncaughtException`. A handler that a listener attaches to the promise does not cancel the event.
- A listener can cancel the event until the microtasks that the listeners queued have run, as in a browser: after `await null` it still counts, after an `await` that waits for a timer or for I/O it is too late. Bun runs these microtasks once, after the last listener. A browser runs them after each listener, so there a second listener sees what a microtask of the first one did. Where Bun reports a rejection from inside a running callback, the listener has to cancel before it returns. That is so for a [`Bun.cron`](/runtime/cron#error-handling) job whose promise rejects after its first `await`.
- Bun reports rejections from the event loop, when the callbacks that were due and their microtasks have run. A handler that another callback of the same turn attaches is in time, and nothing is reported. A browser queues a task for the report, and Node.js reports after each callback.
- [`rejectionhandled`](https://developer.mozilla.org/en-US/docs/Web/API/Window/rejectionhandled_event) is dispatched when a promise that was reported gets its first handler later, before `process.on("rejectionHandled")` is told. It cannot be canceled. It is not dispatched for a handler that an `unhandledrejection` listener, or a microtask of one, attached. If the `unhandledrejection` of the promise was canceled, `process` hears of neither.
- A [`Worker`](/runtime/workers#unhandledrejection) dispatches both events on its own global object. A rejection in a `node:vm` context or a `ShadowRealm` is reported on the global object of the thread.
- What a listener throws is an uncaught exception, like what a listener of any other event throws. With a `process.on("uncaughtException")` listener, the other listeners and `process` are still asked about the rejection. Without one, the exception ends the process with exit code 1, and it ends a `Worker` before the other listeners are called.
- The thread of [`bun test`](/test/runtime-behavior#custom-error-handling) that runs the tests does not dispatch the two events. Neither does a [macro](/bundler/macros).
- A listener that cancels the event and reports in a timer or a request loses that report when the rejection happens in the last callback of the program: Bun reports the rejection when nothing else is left to run, and the process ends when the listeners have returned.

These are not reported through the two events:

- The rejection of the entry module, for example of a top-level `await`. It is an uncaught exception. With `--hot`, a reload that fails is reported through `unhandledrejection`, and the first load is not.
- A promise that an `async` listener of an event of the global object returns, and that rejects. It is an uncaught exception too.
- An uncaught exception. On the main thread it dispatches no `error` event on the global object.
- An error in a [`Bun.serve`](/runtime/http/error-handling) handler, which goes to the `error` handler of the server.
- A rejection that the `onError` of a [`Bun.ModuleGraph`](/runtime/module-graph#errors) takes.
