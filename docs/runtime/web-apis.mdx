Some Web APIs, like the [DOM API](https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API#html_dom_api_interfaces) and [History API](https://developer.mozilla.org/en-US/docs/Web/API/History_API), aren't relevant in a server-first runtime like Bun. Many others are broadly useful outside the browser; when possible, Bun implements these Web-standard APIs instead of introducing new ones.

Bun partially or completely supports the following Web APIs.

## Web Storage

`sessionStorage` is a [`Storage`](https://developer.mozilla.org/en-US/docs/Web/API/Storage) that lives as long as the process. Every `Worker` has its own.

```ts
sessionStorage.setItem("theme", "dark");
sessionStorage.theme; // "dark"
sessionStorage.length; // 1
```

`localStorage` is kept in a file, and is a global only when `--localstorage-file` says which file. Without the flag `localStorage` is not defined.

```ts counter.ts
const runs = Number(localStorage.getItem("runs") ?? 0) + 1;
localStorage.setItem("runs", String(runs));
console.log(`run ${runs}`);
```

```sh
$ bun --localstorage-file=./local-storage.db counter.ts
run 1
$ bun --localstorage-file=./local-storage.db counter.ts
run 2
```

- The file is an SQLite database in the format that Node.js uses for its `--localstorage-file`, so the two runtimes can share one. It is created the first time `localStorage` is used. A relative path is resolved against the directory that the process started in.
- Several processes, and the `Worker`s of a process, can have the same file open. Each of them sees what the others write. The flag is for the whole process: a `Worker` cannot be given another file.
- `--localstorage-file=:memory:` is a `localStorage` that is not written anywhere, which is what a test run usually wants: `bun test --localstorage-file=:memory:`.
- A storage holds up to 10 MB of keys and values, counted as two bytes per UTF-16 code unit. A write that would go past that throws a `DOMException` named `QuotaExceededError`.
- Neither belongs to a request or a user. Everything that runs on a thread has the same `sessionStorage`, and everything that opens the file has the same `localStorage`, so a server should not put the data of one request or one user into them. With `:memory:` every `Worker` has a `localStorage` of its own.

## FileReader

[`FileReader`](https://developer.mozilla.org/en-US/docs/Web/API/FileReader) reads a `Blob` or a `File` and reports the outcome with events. It is there for code and libraries that were written for the browser, for example a library that takes the `File` of an upload. New code can call [`blob.text()`, `blob.arrayBuffer()` and `blob.bytes()`](/runtime/file-io#reading-files-bun-file) instead.

```ts
const server = Bun.serve({
  async fetch(request) {
    const form = await request.formData();
    const file = form.get("avatar") as File;

    const reader = new FileReader();
    const loaded = Promise.withResolvers<string>();
    reader.onload = () => loaded.resolve(reader.result as string);
    reader.onerror = () => loaded.reject(reader.error);
    reader.readAsDataURL(file);

    return new Response(await loaded.promise); // data:image/png;base64,iVBORw0KGgo...
  },
});
```

- `readAsArrayBuffer()`, `readAsText()`, `readAsDataURL()` and `readAsBinaryString()` take any `Blob`, including a [`Bun.file()`](/runtime/file-io). `readAsText()` decodes with the encoding it is given, then with the `charset` of the blob's type, then as UTF-8. A byte order mark wins over all three. `readAsDataURL()` uses `blob.type` as it is, and Bun gives some text types a charset: a `text/plain` blob reads as `data:text/plain;charset=utf-8;base64,...`.
- A read fires `loadstart` when the first chunk has arrived, then `progress`, then `load` and `loadend`. `progress` is fired for the first chunk, then at most every 50 milliseconds, and once more when all of the blob has been read. The read goes on when the listeners of an event have run, so `abort()` in a `progress` listener stops it there. Every event is a [`ProgressEvent`](https://developer.mozilla.org/en-US/docs/Web/API/ProgressEvent), which is a global too, with the bytes read so far in `loaded` and the size of the blob in `total`.
- A read that fails fires `error` and `loadend`, and no `loadstart` when it fails before its first chunk. `reader.error` is then a `DOMException` named `NotFoundError` for a file or an S3 object that does not exist and `NotReadableError` otherwise. Its `cause` is the error of the file system or of S3.
- `abort()` fires `abort` and `loadend` before it returns, and sets `reader.error` to an `AbortError`.
- A second read on a reader that is still reading throws an `InvalidStateError`. Use one reader for each blob, or wait for `loadend`.
